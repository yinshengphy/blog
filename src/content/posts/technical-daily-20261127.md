【高级面试题｜2026-11-27】
【今日方向】：分布式理论与架构

## 一、场景 + 结论

**面试题：**  
某电商大促中，订单服务、库存服务、支付服务分别部署在不同机房，通过 Kafka 异步通信。约束如下：

- 订单创建接口必须在 200ms 内返回；
- 库存不能超卖，支付不能重复扣款；
- Kafka 允许重复投递、分区故障和消费端重启；
- 数据库可能主从延迟，服务可能在“数据库提交成功但消息发送失败”后宕机；
- 不允许依赖全局分布式事务，且订单、库存、支付由不同团队维护。

故障现象是：少量订单长期停留在 `支付中`，库存已扣减但订单未支付；重试后偶发重复扣库存，支付渠道也出现重复请求。

**请你设计整体一致性方案，并说明为什么它不能简单宣称“ exactly once ”。**

**一句话结论：**  
生产上应采用“本地事务 + Outbox/Inbox + 幂等状态机 + Saga 补偿”的最终一致性方案，把消息重复、服务重启和局部成功转化为可重试、可观测、可人工介入的确定性状态流转。

## 二、核心原理

1. **不能依赖分布式 exactly-once**  
   Kafka 的 exactly-once 通常只覆盖特定消息链路，无法覆盖数据库、支付渠道和外部 HTTP 服务；真正的目标应是“业务效果最多生效一次”。

2. **本地事务保证业务数据与待发送事件一致**  
   创建订单时，在同一个数据库事务内写入订单和 Outbox 事件。即使事务提交后进程宕机，事件仍可被后台投递。

3. **消费端必须幂等**  
   每个业务事件携带全局 `eventId`；消费端用 Inbox 表唯一约束，或业务单号 + 操作类型唯一约束，防止重复扣库存、重复记账。

4. **状态机约束合法迁移**  
   订单不能通过重试从 `已支付` 回到 `待支付`；库存补偿也必须有明确状态，例如 `已扣减 → 已释放`，不能无限重复释放。

5. **Saga 处理跨服务失败**  
   下单、扣库存、支付、发货不是一个全局事务，而是一组可正向执行、可反向补偿的本地事务。

## 三、关键实现与工程取舍

### 1. Outbox：解决“提交成功但消息没发出”

```java
@Transactional
public void createOrder(CreateOrderCmd cmd) {
    Order order = Order.pending(cmd.orderId(), cmd.userId(), cmd.amount());
    orderRepo.insert(order);

    OutboxEvent event = OutboxEvent.of(
        UUID.randomUUID().toString(),
        "OrderCreated",
        order.id(),
        json(order)
    );
    outboxRepo.insert(event);
}

// 独立投递线程：可重复发送，消费者必须幂等
public void publishPending() {
    for (OutboxEvent e : outboxRepo.lockBatch(100)) {
        try {
            kafka.send(e.type(), e.aggregateId(), e.payload()).get();
            outboxRepo.markSent(e.id());
        } catch (Exception ex) {
            outboxRepo.increaseRetry(e.id(), nextBackoff(e));
        }
    }
}
```

投递表至少需要：`event_id`、`aggregate_id`、`status`、`retry_count`、`next_retry_at`、`last_error`。  
不要在数据库事务中直接发送 Kafka，也不要以“发送成功”作为数据库提交条件。

### 2. Inbox：解决重复消费

```sql
create unique index uk_consumer_event
on inbox(consumer_name, event_id);
```

消费流程：

1. 开启本地事务；
2. 插入 Inbox，冲突则说明已处理，直接确认消息；
3. 校验订单当前状态和版本；
4. 更新库存或订单；
5. 提交事务后再确认 Kafka 消息。

支付请求还要向渠道传递稳定的 `merchantOrderNo` 或 `idempotencyKey`。因为支付渠道可能超时但实际已扣款，超时后不能直接再次扣款，而应先查询支付结果。

### 3. 并发控制

- 库存扣减使用条件更新：`where available >= quantity`；
- 高竞争商品按 SKU 分区，保证同一 SKU 事件有序；
- 订单状态使用版本号或条件更新，避免旧消息覆盖新状态；
- 不把全局锁作为主要方案，否则会放大延迟和故障范围。

### 4. 工程取舍

- **Outbox + 轮询**：简单可靠，但数据库有额外扫描压力；
- **CDC 订阅 Outbox**：实时性更好，但引入 CDC 链路和运维复杂度；
- **同步调用**：用户感知快，但级联故障明显；
- **异步 Saga**：吞吐和隔离性好，但状态复杂、最终一致；
- **重试**：只能处理暂时性故障，必须配合退避、熔断、死信和人工补偿。

## 四、故障边界、监控与排障

### 1. 关键故障边界

- **DB 提交前宕机**：订单和 Outbox 一起回滚，客户端可安全重试；
- **DB 提交后、消息发送前宕机**：Outbox 扫描补发；
- **消息已发送、状态未标记宕机**：重复发送，由 Inbox 幂等；
- **消费业务提交后、确认消息前宕机**：重复消费，由 Inbox 幂等；
- **支付请求超时**：不能盲目重试扣款，必须按幂等号查询渠道状态；
- **库存成功、支付永久失败**：触发释放库存的补偿事件；
- **补偿也失败**：进入重试队列或死信，并允许人工按业务单号重放。

### 2. 监控指标

按 `orderId/eventId/traceId` 贯穿链路，重点监控：

- Outbox 未发送数量、最老事件年龄、发送失败率；
- Kafka consumer lag、重平衡次数、死信数量；
- Inbox 冲突率、重复消费率；
- 各状态停留时长，如 `支付中` P99；
- 库存扣减失败率、补偿成功率；
- 支付请求超时率、渠道查询与扣款结果不一致数；
- Saga 长事务数量和人工介入数量。

### 3. 排障顺序

先查订单状态机，再按 `orderId` 查 Outbox、Kafka offset、Inbox、库存流水和支付渠道流水：

1. Outbox 是否生成；
2. 是否成功投递、是否积压；
3. 消费是否执行、是否因幂等被跳过；
4. 数据库事务是否提交；
5. 支付渠道最终状态是什么；
6. 是否存在补偿事件及其结果。

禁止直接改订单状态；应优先执行可审计的重放、查询或补偿命令。

## 五、常见追问

- 为什么不用 Seata/XA？  
  外部支付不受同一事务管理，长事务还会降低可用性；分布式事务只能缩小局部一致性问题，不能替代幂等和补偿。

- Kafka 顺序能否保证？  
  只能保证单分区内顺序；应使用业务主键作为消息 key，并避免跨分区依赖顺序。

- 如何防止补偿和正向消息乱序？  
  使用状态版本、事件版本或状态机条件更新；旧版本事件直接丢弃或转人工核查。

- 最终一致性多久算失败？  
  不能只看固定超时，应结合业务 SLA；超过阈值进入告警、死信和人工处理。
