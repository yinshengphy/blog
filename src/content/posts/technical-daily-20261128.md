【高级面试题｜2026-11-28】
【今日方向】：系统设计与高并发架构

**题目：秒杀下单系统如何保证不超卖且可恢复？**

某电商大促中，单个 SKU 库存 10 万件，开售瞬间流量峰值 80 万 QPS，用户可能重复点击、重试或并发下单。现有链路为：API 网关 → 订单服务 → MySQL，库存扣减与订单写入在同一事务中。故障现象是：数据库 CPU 100%、接口 RT 从 50ms 升至 8s，出现库存负数、重复订单；部分用户已支付但订单状态仍为“待支付”。请设计系统，并说明一致性、削峰、幂等、故障恢复和监控方案。

**一句话结论：**前置限流与 Redis 原子预扣削峰，MQ 异步创建订单，数据库用唯一约束和状态机兜底，结合超时补偿与对账实现“库存不超卖、订单最终一致、结果可恢复”。

**核心原理**

1. 请求先经过限流、资格校验和幂等校验，不能让 80 万 QPS 直接打 MySQL。
2. Redis 只承担高并发库存闸门，不作为最终事实源；库存成功后投递订单消息。
3. 订单服务消费消息，使用业务唯一键 `userId + skuId + activityId`，数据库唯一索引防重复。
4. 库存扣减、订单状态、支付结果采用状态机；支付回调必须幂等。
5. Redis、MQ、DB 之间不能假设强一致，依靠可靠消息、补偿任务和定期对账收敛。

**关键实现**

Redis 预扣必须是单条 Lua 原子操作，避免“检查库存”和“扣减”之间被并发穿透：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock <= 0 then
  return 0
end

local userKey = KEYS[2] .. ARGV[1]
if redis.call('SET', userKey, '1', 'NX', 'EX', ARGV[2]) == false then
  return -1
end

redis.call('DECR', KEYS[1])
return 1
```

返回值分别代表成功、重复请求、无库存。成功后写入带唯一业务 ID 的订单消息；生产端使用本地消息表或 Outbox，避免“数据库已提交但消息未发送”。

数据库关键约束：

```sql
ALTER TABLE orders
ADD UNIQUE KEY uk_biz (user_id, sku_id, activity_id);

ALTER TABLE inventory
ADD CHECK (available >= 0);
```

消费者失败可重试，但必须有最大次数、死信队列和人工/自动补偿，不能无限重放。

**工程取舍**

- Redis 预扣换取吞吐，但会出现“占库存未成单”；支付超时、取消订单时通过延迟消息释放，释放操作也必须幂等。
- MQ 削峰后订单延迟增加，应明确 SLA，例如 99% 请求 3 秒内返回“排队中”，而不是同步等待最终订单。
- 强一致事务链路更简单但吞吐低；最终一致方案复杂，却能隔离流量洪峰。
- Redis 库存初始化、重启恢复和热 Key 要有机制；不建议把数据库库存简单定时全量覆盖 Redis，否则可能覆盖已发生的扣减。
- 热点 SKU 可拆分库存桶或分片 Key；但分桶会增加汇总和回滚复杂度。
- 支付成功不等于订单一定已创建：支付单必须携带业务订单号，支付回调可先落支付事实表，再由补偿任务关联订单。

**故障边界**

- Redis 不可用：关闭秒杀入口或切换到保护性拒绝，不能直接打穿 MySQL。
- MQ 不可用：Outbox 持久化待发送事件，恢复后补发；前端返回“处理中”。
- 消费者重复消费：唯一索引、状态条件更新和消费幂等表共同防护。
- Redis 扣减成功但消息丢失：通过 Outbox、库存预扣记录和对账任务找出孤儿扣减并释放。
- DB 提交成功但响应超时：客户端重试必须返回原订单结果，不能再次创建。
- 支付回调乱序：只允许合法状态迁移，例如 `待支付 → 已支付`，禁止已取消订单被无条件改回已支付；异常进入人工审核或退款流程。

**监控与排障**

重点指标：网关 QPS/拒绝率、Redis Lua 延迟和命中率、库存预扣成功率、MQ 堆积/消费延迟/重试数、订单创建成功率、DB CPU/锁等待/连接池、支付回调延迟、重复单数、负库存数、孤儿预扣数及对账差异。

排查顺序：先看限流和 Redis，再看 MQ 堆积与消费者吞吐，随后检查 DB 锁等待、慢 SQL 和唯一键冲突，最后核对支付、订单、库存三方流水。禁止只通过重启消费者或批量改库存“止血”，必须保留业务流水。
