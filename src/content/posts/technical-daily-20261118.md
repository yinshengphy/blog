【高级面试题｜2026-11-18】
【今日方向】：软件工程能力与架构演进

### 场景 + 面试题

你负责一家电商公司的交易平台架构演进：原有单体系统同时处理订单、库存、支付和履约，计划在不能停机的情况下，逐步拆出订单服务与库存服务。

生产约束如下：

- 峰值 1 万 TPS，订单核心链路 P99 低于 300ms；
- 老系统使用 MySQL，暂时不能改造为分布式事务；
- 消息队列只能保证“至少一次投递”，不能保证全局有序；
- 支付渠道是外部系统，回调可能重复、延迟或乱序；
- 新旧系统必须并行一段时间，不能一次性切流；
- 库存绝不能超卖，但允许少量订单进入人工审核；
- 要求具备灰度、回滚、数据校验和故障恢复能力。

上线“订单服务 + 库存服务”后，出现以下现象：

1. 用户已支付，但订单仍显示“待支付”；
2. 少量订单重复扣库存；
3. MQ 消费延迟升高时，库存与订单状态不一致；
4. 重试某些失败消息后，偶发出现重复发货。

**问题：请你设计这次架构演进方案，并说明如何保证数据最终一致、支持灰度与回滚，以及如何定位上述故障？**

### 一句话结论

不要追求跨服务的“强一致和 exactly-once”，应以领域状态机为核心，通过本地事务消息、幂等消费、可补偿 Saga、灰度切流和对账机制，构建“可恢复的最终一致系统”。

### 核心原理与关键实现

**1. 先划分业务事实，再拆服务**

订单服务只负责订单状态与支付意图；库存服务只负责库存预占、确认、释放；支付回调以支付渠道事实为准。通过防腐层隔离旧单体模型，避免新服务直接共享旧表。

关键状态必须单向演进，例如：

`待支付 → 已支付 → 库存已预占 → 待履约 → 已发货`

异常状态单独建模：

`支付未知、库存预占失败、补偿中、人工审核`

禁止消费者根据消息到达顺序直接覆盖状态，必须校验“当前状态 + 事件”是否允许转换。

**2. 用 Outbox 消除数据库与消息队列双写问题**

订单状态和待发送事件在同一个本地事务中提交，再由发布器可靠投递。发布失败只会造成延迟，不会造成“数据库已改、消息永远丢失”。

```java
@Transactional
public void markPaid(PaymentCallback cb) {
    PaymentRecord p = paymentRepo.findOrCreate(cb.id());
    if (p.isProcessed()) return;          // 支付回调幂等
    p.markProcessed(cb.amount());

    order.transition(PAID);               // 状态机校验
    outbox.save(new Event(
        UUID.randomUUID(), order.id(), "OrderPaid", order.version()));
}

@KafkaListener
public void onOrderPaid(Event e) {
    if (inbox.exists(e.id())) return;     // 消费幂等
    txTemplate.execute(s -> {
        inventory.reserve(e.orderId());
        inbox.save(e.id());
        return null;
    });
}
```

实际实现中还需使用唯一索引，例如 `payment_callback_id`、`event_id`、`order_id + reserve_operation`，不能只依赖应用层判断。

**3. 用 Saga 而不是分布式锁或分布式事务**

库存预占成功后支付失败，则释放库存；支付成功但库存不足，则进入人工审核或退款流程。外部支付回调为“事实输入”，不能假设调用成功就等于支付成功。

### 工程取舍

- Outbox 会引入发布延迟和表膨胀，需要分区、归档和积压告警；
- 幂等表会增加存储成本，但这是至少一次投递下的必要成本；
- Saga 允许短时间不一致，换来更高可用和更低耦合；
- 库存扣减可采用数据库条件更新：`available >= n`，避免依赖分布式锁；
- 读模型允许异步更新，但支付、扣库存等关键写操作必须由唯一业务命令驱动；
- 灰度期间必须明确唯一写入源，禁止新旧系统同时扣库存。

### 灰度、回滚与故障边界

采用“旁路校验 → 双读比对 → 小流量切写 → 全量切写”的演进顺序：

1. 新服务先消费事件，但不产生业务副作用，只做影子计算；
2. 对新旧结果做差异比对，确认状态机和库存规则一致；
3. 按商户、用户或订单号灰度，路由规则必须稳定；
4. 灰度阶段由一个系统作为唯一写入源，另一个系统只读或接收同步结果；
5. 回滚只回滚流量，不回滚已经发生的支付、扣库存等事实；通过补偿事务收敛状态。

不能回滚的边界包括：外部支付已成功、仓库已出库、第三方物流已受理。此时只能走退款、释放库存、拦截发货或人工处理，不能伪造“事务回滚”。

### 监控与排障

建立贯穿订单、支付、库存和消息的 `traceId`、`orderId`、`eventId`，重点监控：

- 订单状态停留时间、支付成功但订单未更新数量；
- Outbox 未发布数量、发布重试次数；
- MQ 消费延迟、重试次数、死信数量；
- 库存预占成功率、重复操作拦截数；
- 订单—支付—库存三方对账差异；
- 补偿成功率、人工审核量和恢复时长。

排查顺序：

1. 以 `orderId` 查询状态机变更日志；
2. 检查支付回调是否到达、是否被幂等误判；
3. 检查 Outbox 是否生成、是否发布、是否进入死信；
4. 检查库存操作流水和唯一幂等键；
5. 对比消息时间、消费时间、数据库提交时间；
6. 通过定时对账任务修复可自动修复项，其余进入人工队列。

### 常见追问

- **如何保证消息顺序？**  
  只对同一订单按 `orderId` 分区；但业务仍必须依靠版本号和状态机防乱序，不能只依赖 MQ 顺序。

- **为什么不直接使用分布式事务？**  
  外部支付无法纳入统一事务，且长事务会降低吞吐；本地事务 + 补偿更符合故障现实。

- **如何防止重复发货？**  
  发货命令使用全局幂等号，仓储侧以订单号或履约单号建立唯一约束，并在出库前再次校验订单状态。
